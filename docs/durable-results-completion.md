# Accept and complete

Accept remains an append-only result disposition. It does not change a task. The separate Accept and complete action combines human acceptance of one exact saved handoff with the existing task completion operation.

Current storage calls dispositions `work_result_decisions`, with the `workResultDecisions` Drizzle export and schema-derived `WorkResult*` types. Decisions can be attributed to a human, agent, or system. Accept and complete remains a human action. The feature branch's development naming migration preserved existing records and relationships. Main's released migration history is preserved separately, and the release delta is deferred as described in [storage integration](durable-results-storage.md). The public result path and request contract remain unchanged.

`POST /api/results/:id/complete` accepts a stable `requestId`, the current `expectedStatusChangedCount`, an optional `taskId` when exactly one eligible linked task exists, and an optional note. Multiple eligible linked tasks require an explicit task choice. It also accepts the existing `acknowledgedChildIds`, `runtimeChoice`, and `acknowledgedExecutionIds` acknowledgments.

Exact-result reads expose `completionOptions`. Its task choices come from the result's saved task membership, rather than the execution's current associations. Consider, Done, and Archived tasks are ineligible. A task already completed by this same saved result is excluded, including recurring tasks. An independent result or ordinary conversation does not make a handoff stale. A successor does.

Before completing code work, Ri observes the authorized source execution through its existing computer and folder handle. Retained execution provenance remains useful after the source conversation is pruned. A known commit, checkpoint, or working-copy state mismatch rejects completion. Dirty contents without an exact checkpoint and unavailable observations remain explicitly unknown. This action does not claim those contents are fresh.

The query uses one immediate home-database transaction to write acceptance and call the existing `completeTask` lifecycle. Revision, linked-task, successor, and child guards are checked again inside that transaction. Failure rolls back both writes. Completion uses the existing task completion and status-change ledgers, including recurrence, history, and actor attribution. It adds no table or lifecycle engine. The status-change reason `Accepted saved result <id>` is the retained relationship used to exclude another occurrence for the same result and task.

Runtime coordination follows the normal task completion path. The server validates the operation before presenting or applying the existing open-child and running-workstream choices. Explicit Stop preserves the workstream and its other task associations. A failed Stop leaves the acceptance and task unchanged. Keep running changes the task and informs the author of the scope change. Database and observed revision guards run again after that asynchronous coordination.

The completion-specific request identity and intent hash bind the exact result, selected task, expected revision, note, and confirmations. Identical committed retries return the original acceptance and recorded lifecycle outcome before checking current gates, membership, or source availability. Changed intent conflicts. A deleted task can leave a retained acceptance with no available completion task record. The client retains the original submitted payload for uncertain retries, so it cannot turn a lost response into a second recurring occurrence.

The suite in `src/lib/work-results/completion.test.ts` covers atomic rollback, eligible task selection, supersession, code scope, task revisions, recurrence, concurrent retries, pruning, disabled gates, actor attribution, open children, and runtime choices. `src/lib/work-results/observe.test.ts` covers ownership before execution-computer access. Recorded verification in [the personal integration document](durable-results-personal.md) predates the internal naming migration.
