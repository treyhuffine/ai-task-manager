# Local apps: implementation contract

October 7, 2026, updated October 8. The local MVP is implemented in Ri, with Finances source in the same checkout. Qualification evidence is in [the verified checklist](local-apps-progress.md), and launch instructions are in [the runbook](local-apps-runbook.md). Start with [the handoff](local-apps-handoff.md). This is the normative MVP companion to [the product direction](local-apps.md). [Finance integration](local-apps-finance.md) specifies the first independently developed service app. [Modularity](local-apps-modularity.md) specifies the reusable engine boundary and extraction gates. The historical plugin evaluations supply evidence, not additional acceptance requirements.

## 1. Release boundary and order

October 8 implemented extension: [app and Connector mentions](app-connector-mentions-spec.md), with [separate qualification evidence](chat-sources-progress.md), adds Ri-owned source chips and dispatch under `RI_CHAT_SOURCES`. The shared layer and Connector adapter build and work without the local runtime, builder, app-kit or Finances. The optional local source adapter requires both flags. Node packages may omit `ui` when they declare at least one action. Static packages still require a view. Both Node adapters support tools-only packages, with a native summary and fixture Try experience. Earlier checked slices below cover the original runtime. Production connected MCP views remain a separate pending extension.

Apps are enabled by default. `RI_LOCAL_APPS=0` disables the runtime, builder, app routes and tools together. Availability is evaluated on the Home, never from browser input, through one shared lightweight helper. Keep the implementation removable and qualify changes with disposable Homes. Initial qualification is on the current macOS Apple Silicon Home, its pinned Node runtime, the desktop viewer, and an ordinary browser. Other targets require the same tests before being advertised. Remote viewers use the Home's existing authenticated connection, never a service port on the viewer's computer.

The first useful release includes creating and changing a small app inside Ri, persistent data, a real preview, contextual use from existing chats, bundled workflow skills, scoped Gmail reads, a scheduled action, portable package export, and removal. Finance follows as the first included service app in the same implementation sequence. A public marketplace, standalone consumer builder, arbitrary service installers, new languages, and strong isolation for hostile code are outside this release. Owner-trusted local code is the explicit execution profile, including builds and dependencies. The package boundary is required now, while extracting it into another repository is not.

Keep three runtime cases, with only two backend adapters:

| Manifest runtime | Execution | Intended use |
| --- | --- | --- |
| `static` | No backend. One bundled HTML resource | Calculators, reference tools, visualizations |
| `node` with `ri-ipc-v1` | Pinned Node child, typed request/reply over its private IPC channel | Default generated app, files or `node:sqlite` |
| `node` with `mcp-http-v1` | Supervised Node service, private loopback MCP endpoint, lifecycle/bootstrap IPC | Existing Finance app, later other qualified service packages |

The service adapter ships with the Finance slice. Do not make a generated tracker run another Next.js server. Do not rewrite Finance into the small-app template just to host it.

## 2. Files and authoritative metadata

Scope: the file layout and instance registry below belong to Ri-managed packages. [Connected MCP apps](app-connector-mentions-spec.md#9-connected-mcp-apps-and-a-common-view-host) are projections over existing integrations and exact accounts. They never need fake installed instances, a local data directory or a Ri service bootstrap. Their qualified MCP Apps browser host is shared with local apps but independently retainable, with production hosting tracked as a pending extension. Keep standard MCP results/context in the common host and local manifest/resolver conventions in the local adapter.

Add helpers beside the existing path helpers. All paths derive from `getAppRoot()`, `getConfigDir()`, or `getWorkDir()`:

```text
<app-root>/apps/<instance-id>/
  package/                   active, validated source and runtime artifact
  data/                      durable app-owned files
  cache/                     disposable files
  logs/                      bounded output, private by default
<app-root>/app-drafts/<draft-id>/
  package/                   editable source, lockfile, docs and build output
  data/                      independent preview records
<config-dir>/local-apps/state.json
<work-dir>/local-apps/        ephemeral process ownership and transport records
```

An installed ID and draft ID are UUIDv7 values generated by Ri. Never turn a slug or caller-supplied filesystem path into a data directory. A slug matches `[a-z][a-z0-9-]{0,47}`, is unique across active and archived instances, and reserves `new` and `drafts`. Instance IDs survive renames and upgrades. MVP permits one installed instance per package ID. The storage model does not assume that restriction forever.

`state.json` is a strict, versioned JSON document, not a second user-record database. Use `atomicWriteFile` with the existing `withFileLock` and an in-process queue held in `processState`. The running Home is its only writer. CLI/orchestrator mutations call the Home. Never hold the file lock while awaiting app code, provider calls, or a build. Store an incrementing revision and reject stale management edits. The revision tracks management changes. Invocation summaries, data-change notifications and claimed schedule slots use the same atomic writer without invalidating a settings review. This avoids preview polling conflicting with activation. Unknown versions or corrupt metadata stop app operations with a repairable error, never overwrite the file with an empty registry.

| Record | Required contents |
| --- | --- |
| Root | `formatVersion: 1`, `revision`, instances, drafts, grants, schedules, chat panels, bounded invocation summaries |
| Instance | ID, slug, package ID/version/digest, enabled/archived state, creation/update times, activation state, source provenance, customized flag |
| Draft | ID, source instance or null, source package digest, builder/try chat IDs, associated skill draft refs, last validated artifact digest, build status, optional catalog package ID/artifact digest/name |
| Grant | ID, instance ID, principal kind/ID, allowed app actions, named Ri capabilities, connection bindings, revision, revoked time |
| Schedule | ID, instance ID, action, schema-validated input, cron, timezone, active hours, enabled state, next run, explicit job grant ID |
| Chat panel | ID, chat ID, instance ID, internal path/query, optional named view reference. At most one panel per chat. No bearer credential or live selection payload |
| Invocation summary | UUID, instance/action/actor, package digest, grant revision, schedule/slot if any, start/end times, outcome, redacted error |

Every record has `createdAt` and `updatedAt`. Derive TypeScript types from the feature's Zod schemas. These are file records, not new core Drizzle tables. Bound metadata to 100 instances, 20 schedules per instance, 200 chat panels, and the latest 100 invocation summaries per instance for this trial. Closing a panel or archiving its app/chat removes the panel binding. Refuse a new panel at the limit with a useful close-panel action, never silently drop another chat's binding. Prune completed summaries, never a live invocation. Do not retain request bodies, email, receipts, or tool results in this activity list. Runtime view sessions and live context snapshots are separate bounded ephemeral state in `processState`.

Core `chat_sessions.surfaceKind` and `surfaceRef` are already text columns. Use those existing fields for app chats. No core schema migration is required for registration, app schedules, grants, or builder context. New persistence requirements must update this decision before implementation expands the schema.

Included-app setup is durable. Preview app creates a draft with catalog provenance, and Continue setup reopens that draft across refresh or Home restart. Repeated concurrent requests reuse the same matching draft after archive integrity checks. An existing installed, disabled or archived instance is shown as such instead of being silently installed again. Activation remains the explicit Use app step.

## 3. Package v1 and generated contract

An export contains a portable Agent Plugins `plugin.json`, `contract.json`, `README.md`, `AGENTS.md`, optional `skills/`, source, and the declared build inputs/artifacts. A qualified external MCP target can also include standard `mcp.json`. It contains no Home IDs, grants, account bindings, credentials, records, private chats, caches, or logs. The portable manifest's `name` and `version` are the authoritative package identity and version. Use kebab-case names, initially `local-<name>` for personal packages and `ri-<name>` for maintained starters. These labels are not verified publisher claims. Installed UUIDs remain distinct.

Use the published Agent Plugins 1.0 schema profile, vendored and digest-pinned with the app kit so validation needs no network request. Validate Ri's proposed `extensions.com.ri` strictly. Preserve other extension namespaces as inert package data, never execute them or treat them as Ri permissions. There is no second `app.json` or duplicated identity. A package without the Ri runtime extension cannot be installed as a runnable local app in this release. Explain its unsupported target instead of executing arbitrary MCP commands. Standard standalone skill management remains available through its existing surface. [Portable package layout](https://developers.openai.com/plugins/build/plugins)

Example `plugin.json` for a small app:

```json
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
  "name": "local-receipts",
  "version": "0.1.0",
  "description": "Keep purchase receipts and track follow-ups.",
  "license": "UNLICENSED",
  "extensions": {
    "com.ri": {
      "formatVersion": 1,
      "displayName": "Receipts",
      "hostApi": 1,
      "suggestedSlug": "receipts",
      "runtime": {
        "kind": "node",
        "protocol": "ri-ipc-v1",
        "entry": "dist/server.mjs",
        "start": "on-demand",
        "executionProfile": "trusted-native"
      },
      "build": { "adapter": "ri-esbuild-v1", "lockfile": "pnpm-lock.yaml", "executionProfile": "trusted-native" },
      "ui": {
        "resources": [{ "uri": "ui://local-receipts/main.html", "file": "dist/ui.html" }],
        "entrypoints": ["global", "thread"],
        "resolveAction": "open_view",
        "contextAction": "describe_view_context"
      },
      "contract": "contract.json",
      "requests": {
        "integrations": [
          { "binding": "mailbox", "toolkit": "gmail", "actions": ["gmail.search_messages", "gmail.get_message"] }
        ],
        "riActions": []
      },
      "source": { "kind": "personal" }
    }
  }
}
```

All runtime fields below are inside `extensions.com.ri`. `runtime.kind` is `static` or `node`. Static omits protocol/entry/start/executionProfile, resolveAction, contextAction and backend actions. Node requires protocol/entry/start/executionProfile and resolveAction. `contextAction` is required when a backend view shares mutable selection/filter context. `start` is `on-demand` or `on-home-start`. The latter is shown as background activity during installation. Only the `trusted-native` execution profile is implemented initially. Other requested profiles fail as unsupported, never downgrade. `mcp-http-v1` also requires `runtime.mcpPath`, initially `/mcp`. It still has a Node entry, never a shell command. `ui.resources` is an allowlist of one to eight resource URIs. Local resources name their files. Service resources come from MCP and omit `file`. A static app has one resource. `ui.entrypoints` is a nonempty subset of `global` and `thread`, with both in the default template. Build adapters are `none`, `ri-esbuild-v1`, and the qualified `next-standalone-v1` service build. Unknown adapters fail validation.

Build adapters other than `none` require `build.executionProfile`, independently of whether the final app has a backend. The initial supported value is `trusted-native`. Select and verify the driver before dependency install or build, not just before backend startup. A static HTML runtime does not make its build scripts safe.

Service artifacts declare exactly one `runtime.target`: `{ platform, arch, nodeVersion, nodeAbi }`. `platform` and `arch` name the qualified OS and architecture, `nodeVersion` is the exact supported Node version, and `nodeAbi` is its `process.versions.modules` string. Probe the actual executable the driver will launch before running package code, bootstrap or migrations. Reject a mismatch as unsupported. Native dependencies never fall back to a consumer-machine rebuild.

Manifest paths must be relative, remain inside the package after canonicalization, and contain no symlink escape. Archive import rejects absolute paths, traversal, symlinks, device files, duplicate entries, and excessive expanded size. Initial limit: 100 MiB source/static exports. Service runtime artifacts have a separate 500 MiB limit. Exports use a positive file inventory and exclude private directories and secret files. Review the final inventory and scan for credentials. Source can itself contain sensitive literals, so exclusion rules alone are not a privacy guarantee.

The SDK action definition is the source of truth for runtime registration and `contract.json`. Generate the contract at build time, then validate the artifact without starting it. Include `formatVersion`, package identity/version, action descriptors, entity descriptors, optional per-resource context-state schemas, and a workflow index derived from packaged SKILL.md metadata. Each action has a stable local name, description, strict JSON Schema input/output, allowed audience (`user`, `agent`, `schedule`), effect (`read`, `app_write`, `external_write`), timeout, retry semantics (`read_safe`, `idempotent`, `never_automatic`), errors, and at least one fixture example. Mutating SDK handlers receive an invocation ID. They must persist deduplication where their semantics need it. The bounded host activity history is not permanent business-level deduplication. An annotation is documentation, not a security proof.

Entity descriptors specify type, ID/title fields, read/list/search actions if supported, and an open-path template. All named actions must exist, list/search must paginate, and schemas must describe the returned record. An entity reference is `{ instanceId, entityType, recordId }`. Do not store app records in Ri simply to make links.

For MCP services, generate the static contract from the service's own action definitions in its repository, then check the live `tools/list` and resource identity against the installed artifact at readiness. Preserve MCP Apps UI metadata and app-only tool visibility. The manifest supplies lifecycle/distribution details MCP itself does not provide. Unknown or changed tools do not silently acquire grants.

The kit's development MCP projection maps small-app action definitions to standard tools/resources without a second handwritten registry. Preserve input/output schemas, effects, app/model visibility and error semantics. It runs only in the fixture host for initial qualification, on a private endpoint with fixture authority. Production external access, tunnel setup and public ChatGPT publication are separate adapters, not export side effects. Test the same resource in the Ri controller and a standard MCP Apps reference host. A host compatibility label requires that host's actual workflow and permission tests.

### Bundled workflow skills

Discover `skills/<name>/SKILL.md` using the existing skill parser. Errors block activation. Bound the MVP to 20 bundled skills per package and the normal package inventory limits. Skills refer to the current app through the supplied instance binding, never a hardcoded Home/instance ID. Metadata describes when to use each workflow. Full instructions load on demand, as lower-trust package instructions, and cannot widen tool grants or override host policy.

Extend `src/lib/skills/manage.ts` with a package-resource adapter for authoring, validation and read-only session delivery. New skill authoring still starts through its draft APIs. The app draft records those skill draft refs and packaging copies their validated resources into `skills/`, then hashes them with the rest of the package. Editing an installed bundle stages its skill source through that same manager. There are no direct app-code writes to managed skill locations and no global/project links created by app installation. Do not extend `moveSkill` into an app-process manager. An explicit extraction to a standalone installed skill uses its normal draft/move lifecycle.

Runtime availability is derived from enabled package digest and the chat's app grant, using a namespaced `(instanceId, skillName)` binding. The Ri adapter supplies authorized metadata/resources through the existing session skill/instruction mechanism. A running builder gets maintenance instructions, while an app-use chat gets the relevant workflow skills. App update/archive/revoke invalidates the available bundle before the next turn and recycles harness discovery at an idle boundary where necessary. Previously delivered text cannot be erased from model history, so every tool call still rechecks live authority. Session-only materialization, if required by a harness, is owned by the skill manager and cannot become an ambient global install.

## 4. Supervisor and invocation protocol

The owner is the long-lived Home HTTP/Next server process. Initialize once from `instrumentation.ts`, after validation-mode and Home-identity gates. All route bundles and the custom HTTP host access the same `processState` supervisor. The desktop controller owns that Home process and does not create a competing app registry. CLI/dev launch uses the same lifecycle. A validating build/server and a worker-only device must not start apps.

The supervisor comes from the app kit and is instantiated by the Ri adapter. An execution driver implements `prepare`, `start`, `stop` and `dispose`, returning owned process/transport handles and declared isolation capabilities. Host policy chooses the qualified driver, supplies resolved mounts/directories and broker channels, and checks the manifest's minimum profile. The driver never decides a grant or receives the Home's full authority. The first driver is native Node only. Future contained drivers must pass the same lifecycle tests plus adversarial build/runtime tests before being advertised. An unsupported required profile fails before code execution.

Launch the pinned Node executable with an argument array and a private IPC descriptor, `shell: false`, cwd at the package, and an allowlisted environment. Supply `PATH` for the qualified runtime tools, locale/timezone/temp settings, and private bootstrap data. Do not copy Home bearer credentials, session credentials, integration secrets, `NODE_OPTIONS`, or the full parent environment. An app may still read outside its folder as the same OS user. This is not a hostile-code sandbox.

Host-to-child protocol messages carry `version: 1`, request ID, method, and parameters. Methods are `initialize`, `invoke`, `cancel`, and `shutdown`. Child replies carry matching request ID and either `result` or `{ code, message }`. Child-to-host capability requests carry the active invocation ID and a separate call ID. The host records which child/generation owns the channel and never trusts an instance ID claimed in a payload.

`initialize` supplies resolved data/cache directories, package digest, protocol version, and named capability bindings without provider credentials. `ready` must return the matching protocol/contract digest. For a service, readiness also returns its loopback endpoint and declares its bootstrap operations described in the Finance adapter. No process executes a tool just to discover descriptions.

Invocation context is created by Ri: ID, stable initiating principal, audience, grant revision, deadline, and cancellation signal. A client may reuse its invocation UUID for a retry, but it is only an idempotency key. Bind it to instance, actor, action and input digest, and reject mismatched reuse. An app never supplies its own authoritative caller. Validate both input and output against the installed contract. Connector calls during an invocation inherit that context through the SDK. Out-of-band service work uses a separately granted background principal, not the last viewer's or builder's identity. Recheck authorization before returning any cached result.

Defaults: readiness 30 seconds, one in-flight action per small-app instance, 32 queued calls, 30-second action deadline with a declared maximum of 300 seconds, 1 MiB JSON inputs, 8 MiB JSON results. Reject overload with `busy`. File transfers use bounded host-mediated streams, not giant JSON. Keep 10 MiB of rotating logs per instance. No tool payload logging by default. These are named host constants, not package-controlled resource promises.

Native IPC has no listening port. MCP services bind only `127.0.0.1` on a host-assigned free port, authenticate every call, reject redirects, and are reachable only through their recorded endpoint. Never accept a caller-supplied endpoint or general reverse-proxy path. Allocate/retry port binding at most three times. Public Ri routes do not expose the service's own login, database, or arbitrary Next routes.

Record process generation and ownership. The child exits when IPC disconnects. Graceful shutdown cancels admission, asks the app to drain, then terminates its owned process group after five seconds. The managed service wrapper also stops its descendants. A hard Home crash must not leave Finance monitoring alive under stale authority. Reconcile interrupted invocations on boot. Never signal a stale PID without validating process ownership. Test these cases using real processes on the qualified OS.

An unexpected exit marks the app failed and invocations interrupted. Do not automatically replay them. The next explicit open/run may start a fresh process. Three failed starts in five minutes require a user retry. `on-demand` children remain alive until disable/update/Home shutdown. `on-home-start` children restart with the Home while enabled. Closing an iframe changes neither policy.

Use the existing maintenance/activity gates for invocation and build work. Integrate app draining with `__riPrepareIdle` and await supervisor shutdown in `src/service/http-server.ts` before its final exit. Count active app work in update-idle decisions. A background service being alive is not itself continuous foreground activity.

## 5. One browser host

`/apps` is the library, `/apps/new` starts a draft, `/apps/drafts/<id>` is the builder, and `/apps/<slug>/<path>` opens an installed view. Add the thin catch-all page and a shared app shell with the existing chat components. Keep app/builder state in the URL, server records, and the shared query cache. Do not fork a second implementation of chat. App navigation must not discard unsent input. No refactor of all task/note pages is required.

Follow [Navigation and everyday use](local-apps.md#navigation-and-everyday-use): the persistent Agents/Apps control switches the rail's contents, installed rows open the app directly, and Ask Ri reveals the companion chat. Builder chat/preview is a separate mode. Connectors and Skills link to their existing surfaces. Preserve the current Agents/Recent list under Agents, the current collapsed flyout behavior, URL-driven selection and unsent chat input. `/apps?browse=1` selects the catalog within the library. Package import starts from that library and does not need a new global destination.

Use the same app view controller for a `global` entrypoint and the existing conversation's `thread` panel. `open_app` returns a protected view reference, and the chat presents an explicit Open control rather than executing arbitrary package HTML. Selecting a permitted app in the existing chat's picker or opening that reference creates/updates the chat-panel binding. It does not replace `chat_sessions.surfaceKind` on an ordinary agent/execution chat or create a new conversation. The global Ask Ri flow may create/reuse a content chat with `surfaceKind: 'app'` and `surfaceRef: <instance-id>`. Recheck grants whenever either surface opens. MVP has one companion app per chat and no new file-viewer or composer-search system.

**MVP asset decision:** each view is one self-contained HTML resource with inline bundled scripts/styles and embedded images/fonts. No CDN, relative network assets, guest fetch, service worker, or guest SSR. A raw HTML app and an esbuild React app must both pass. Other frameworks work when they can produce this artifact with supported tooling. Multi-file asset serving is an extension, not an unresolved prerequisite.

Use the MCP Apps `App`/`AppBridge` message protocol for views in both adapters. Small apps use a supplied plain-JavaScript facade and do not need to run an MCP server. The host maps `tools/call` to its ordinary action dispatcher. Service apps keep their MCP UI resource and callback tools. Begin qualification with Finance's current exact versions, `@modelcontextprotocol/ext-apps` 1.2.2 and `@modelcontextprotocol/sdk` 1.29.0. Pin the qualified result rather than following latest implicitly. [MCP Apps overview](https://github.com/modelcontextprotocol/ext-apps/blob/main/docs/overview.md)

Use two host-controlled `srcdoc` frames, each with `sandbox="allow-scripts"` and no `allow-same-origin`. The outer frame contains only Ri's fixed message relay and restrictive CSP. It receives the guest HTML through the bound channel and creates the inner frame. The guest cannot change its containing relay's policy. In particular the outer policy's `frame-src 'none'` prevents the inner frame from navigating to network URLs, including Ri URLs. A guest-only `connect-src 'none'` would not close that navigation path. Both frames have opaque origins. No separate sandbox server or guest access to the parent DOM is needed for this restricted profile. The standard's broader web-host example uses a separate-origin proxy. [MCP Apps basic host](https://github.com/modelcontextprotocol/ext-apps/blob/main/examples/basic-host/README.md)

Fetch the artifact in the authenticated parent, never navigate the parent to app HTML. Parse and validate it, reject external scripts/styles/assets, base elements, meta refresh and guest-defined nested frames. Put the restrictive CSP before any executable content in the relay and guest. The relay's policy must permit the hashes of its fixed relay script and the installed guest bundle, since `srcdoc` inherits its creator's policy. Permit inline styles and data images/fonts. Deny connect, workers, network frames, objects, forms and base URLs. Do not use eval. Explicitly qualify `srcdoc` loading and blocked network navigation together on each supported browser. This is a restricted MCP Apps resource profile, not universal resource compatibility. [CSP inheritance and frame restrictions](https://www.w3.org/TR/CSP/)

Bind each bridge to the exact outer iframe `contentWindow`, an unpredictable view-session ID, package digest, actor, allowed callback names, and selected record scope. The relay accepts only its parent and its specific inner `contentWindow`. Check message source and protocol schema at both hops. The top-level host rejects direct messages from the guest. `origin === 'null'` alone is not identity. Host-to-opaque-frame postMessage may require `'*'` as target origin, but only on that specific window. Destroy the bridge and invalidate its view session on navigation, unload, app update, revoke, or archive. No bearer credential enters either iframe. Bound/rate-limit messages and size notifications. An app cannot request arbitrary Ri tRPC procedures, tools from another app, or an arbitrary HTTP fetch.

Advertise only implemented bridge capabilities. Initially allow app tool calls, initial/refreshed tool result, host theme/size, bounded `ui/update-model-context`, validated internal navigation, and explicit human-triggered opening of external HTTPS links through Ri. Context updates alone never send chat or invoke a model. Do not enable guest-initiated chat sends, sampling, arbitrary resource reads, file access, clipboard, downloads, or popups merely because an SDK supports them. Add upload/download as host-mediated capabilities only when a slice needs them, with normal attachment size/MIME checks and no filesystem path exposure.

`ui.resolveAction` is a read-only opener taking `{ path, query }` and returning `{ resource, data, scope }`. `scope` contains allowed action names and optional exact input bindings, such as `viewId`, which cannot be replaced by guest arguments. The host intersects action names with the installed contract and actor grant, validates the resource allowlist, and stores the scope server-side with the view session. It then supplies `data` as the initial structured tool result. Bind the stable selected record, not its mutable revision. The app continues to check revisions on every write. Static apps receive only path/query/theme. Internal navigation goes through the bridge into the parent URL and invokes the read-only opener again. Reopening, refreshing, and Back never replay a previous mutation. Writes require fresh invocations and the app's normal revision/idempotency checks.

### View context and conversation synchronization

Use standard `ui/update-model-context` messages through the qualified MCP Apps adapter. The app SDK encodes a versioned state envelope in the standard content payload: `{ formatVersion: 1, revision, state }`, with monotonically increasing revision per view session. Validate `state` against that resource's generated context schema. Support selections, filters and staged values, not arbitrary HTML, DOM dumps or system instructions. Limit a snapshot to 8 KiB, selections to 50 entity references, and accept at most ten updates per second per view. Coalesce intermediate changes. Return a typed error for invalid input rather than silently using it.

Bind each snapshot to view-session ID, instance, resource, package digest, initiating actor and chat ID outside the guest payload. A global view has no model-context recipient until its Ask Ri chat is explicitly bound. A thread panel binds only to that thread. Each browser tab has an independent view session. Reject old revisions and attempts to change the binding. A read-only `describe_view_context` action, named by `ui.contextAction`, receives `{ path, query, state }` and returns `{ modelContent, recordRefs, dataRevision }`. Resolve it as the receiving chat's principal, intersected with the view/app scope, even when the human's view has broader account access. The action must validate record access and resolve authoritative values server-side. Do not forward raw owner-visible fields around that check. Inaccessible context produces a clear change-access or remove-context action. Bound the model-facing result to 16 KiB. Its output and staged UI values remain labeled app data, never higher-priority instructions.

On message send, the composer flushes pending context and includes its acknowledged view-session/revision reference with the user input. The server resolves and freezes one authorized snapshot for that turn before handing the message to the harness. Expired/revoked bindings fail with a refresh/remove-context action, without losing the typed message. Do not substitute another tab's latest selection or quietly continue with guessed context. A fresh/opened node view can resolve empty presentation state from its read-only opener. Static views may share only schema-validated presentation state labeled as such, with no claim to authenticated external records.

Context updates do not persist business records. Only a declared action can apply staged edits. Clear live snapshots and invalidate view sessions on close, navigation, package update or revocation. Reopening uses the saved view/path and authoritative data, not a historic tool-call replay. Persisted transcripts retain context already sent, subject to Ri's existing retention semantics. Revocation prevents future access, not retrospective removal of what the user already read.

After a successful app mutation initiated through Ri, emit an instance-scoped change event with identifiers/revisions only. The Ri adapter invalidates affected authorized open views, reruns their read-only opener and forwards a standard tool-result update. Preserve selections/filters when their IDs still exist. If an in-progress edit conflicts, retain it and show a refresh/compare state rather than overwriting it. MVP may invalidate all open views for that instance. Service-owned background changes refresh on focus and through a bounded five-second read while visible, unless a qualified service change notification is available. No hidden-view polling or new model turn is needed. Host services and app-local workers keep their existing lifecycle.

Qualification includes: select two records and ask about "these", change a filter without changing the URL, distinguish a proposed scenario from an applied one, mutate through chat and observe the view refresh, retain a conflicting unsaved edit, isolate two chats/tabs, reject a forged record reference, prevent an owner view leaking into a narrower chat, and handle revocation between context update and send. This protocol is used in both global and thread surfaces. [MCP Apps context and state](https://developers.openai.com/plugins/build/chatgpt-ui#manage-state)

Qualification must demonstrate opaque origin, no parent DOM/cookie/storage/Electron access, blocked fetch/resource loads and form submission, rejection of forged messages, null-origin mutations refused by Ri, and revoked/stale view sessions rejected server-side. Include attempted frame self-navigation and a second tab. A failed containment test blocks the view host slice. A restrictive CSP is not proof against every browser/network side channel. Both app source and dependencies remain owner-trusted for this release. Public hostile-code qualification is a separate gate.

## 6. Calls, grants, and approvals

Keep two directions distinct:

| Direction | Authority |
| --- | --- |
| Human/chat/job → app action | Ri actor grant, action audience, app's own record/account authorization |
| App → Ri tool or connector | Installed app grant ∩ initiating actor scope, selected account binding, live provider authorization and approval policy |

The owner grants connections/actions in Ri's UI. Packages only request access. Store session/workspace app-action grants in feature metadata rather than silently making every installed app readable to every agent. Existing signed chat identity is authoritative. The user can allow a chat to read an app without allowing evidence access or writes. Owner-initiated UI operations have user authority, while callbacks remain limited to their registered view scope. A job has an explicit owner-created grant independent of any chat lifetime. Native account selection is optional package metadata under `ui.access`: its path opens as the human owner with the selected caller in `query.hostActor`, and its declared callback returns `scopeRef`. The opener binds `actorId` server-side, so a guest cannot replace the intended caller. Ri holds the app-issued reference and binds it only on the human’s explicit grant save. No actor IDs or credentials need to be copied for Finance chat access.

For generated apps, IPC carries capability calls. Services use an ephemeral bearer limited to their instance, process generation, and role on `/api/local-apps/broker/v1`. A service call must carry a host-issued invocation ticket for interactive work, or its separate background grant. A background credential cannot stand in for an interactive ticket. Tickets are bound to the app action/actor and expire with the invocation. Nothing accepts the Home token as an app credential. Revocation is checked on every operation and before returning protected results. Work already committed externally cannot be undone by revoking a grant.

Use exact action IDs from the integration registry, account bindings chosen by the human, and `runAction`. A package never chooses a raw provider URL or injects credentials. For MVP the sample needs `gmail.search_messages` and `gmail.get_message`. Unsupported actions fail explicitly. Finance's richer, versioned compatibility operations are specified separately. Task/note access calls existing domain operations, with a narrow allowlist. Bounded AI is a separate capability through the subscription harness helper, not a general model API proxy.

Extend shared integration approval identity from session-or-null to a discriminated principal plus app instance, invocation ID, and broker call ID. Keep the existing owner/action/connection/input digest/action version match and single-use TTL. Preserve current chat behavior. App and job requests appear in app activity, with a badge leading to a working approval card. Do not attach app requests to an arbitrary chat or share the anonymous grant slot.

The SDK handles `approval_required` by suspending only that broker call in memory and showing `waiting_approval`. On human approval, it rechecks authority and retries that exact connector call once, using the same broker call ID. The app handler is not restarted. Pause the action execution deadline while waiting, with a maximum wait of five minutes. Denial/expiry resolves with a typed error. Process restart loses the continuation, expires the approval and marks the invocation interrupted. No silent resumed send. App approvals offer Approve once and Deny in MVP, not a global Always bypass.

Keep small-app serialization during approval waits. The approval card and cancellation control live in Ri's native shell and do not enter the app action queue. An already open view remains visible with a waiting notice. A first open shows a waiting screen with those controls. Pause view refresh polling while waiting, rather than accumulating queued reads. Cancellation invalidates the pending approval and ends its invocation. Dismissing a notice is not cancellation.

Stable errors: `invalid_input`, `not_found`, `forbidden`, `revoked`, `unsupported`, `conflict`, `busy`, `timeout`, `approval_required`, `approval_denied`, `interrupted`, `app_failed`. Domain adapters map to the existing tRPC/orchestrator envelopes, including their narrower `ActionError` codes, without losing the typed reason. Never place raw credentials, input bodies or stack traces in user-visible errors.

## 7. Scheduling and service-owned workers

Register one gated local-app participant in the existing scheduler tick. It uses the scheduler's ownership lock, `computeNextRun`, active hours, and maintenance gate. No additional cron timer. Under the metadata lock, claim a due slot by recording its invocation and advancing `nextRunAt` together, then release the lock before dispatch. Handle at most 20 due app slots per tick so app work cannot starve core schedules. Enforce one running instance action and one invocation per schedule. An overlap records a skipped slot rather than queuing an unlimited backlog.

On wake/start, invoke each overdue schedule at most once and advance from now. Record outside-active-hours skips. Do not replay every missed slot. A crash after claim may mean the slot never ran. A crash after an external write may leave an uncertain result. Mark it interrupted, with explicit retry. This preserves the current scheduler's at-most-once dispatch tradeoff and does not promise exactly-once effects.

Existing service apps may retain their own durable work queue. Finance does. Ri keeps that service alive while enabled and presents its status. Do not schedule the same Finance sync from both Ri and Finance. Ri schedules are for additional user-requested actions, not a rewrite of a service's internal jobs. Incoming public webhooks are not needed for this local MVP.

## 8. Builder, dependencies, activation, and removal

Reuse content chats with `surfaceKind: 'app-builder'` or `'app-try'` and `surfaceRef: <draft-id>`. Resolve builder cwd from the validated draft record before the existing Home-root fallback. A missing draft fails closed rather than dropping the builder into the Home. Add a builder brief through existing harness session instructions. Scope it to the draft, supported SDK/tools, fixtures, documentation, and relevant app contract. Preview and builder authority are distinct. Resuming after navigation restores the same chat/draft. The existing skill manager owns bundled skill authoring/validation/delivery through its package adapter, while app lifecycle remains with local apps.

Ship a pinned build kit with the Ri runtime: pnpm, TypeScript, esbuild, the app SDK/bridge, React template, raw HTML template, and the qualified Node SQLite wrapper. Put its reusable source in `packages/app-kit` and add that exact package explicitly to `pnpm-workspace.yaml`, which currently includes only the integrations package. Produce an independent package/build artifact. Do not depend on globally installed pnpm/tsx or Ri's application `node_modules`. A generated package has its own lockfile. Initial install from the package registry needs network access, with a clear offline error and retry. Reusing a populated package cache is optional.

Allow only the known build adapter and lockfile install with lifecycle scripts disabled. Unknown native build steps fail with an unsupported-dependency explanation. Qualified service artifacts can contain native modules built for their exact OS/architecture/Node ABI. They are never installed opportunistically into Ri. Build sandboxing remains a future security boundary. Bundle building/code execution runs in separate processes with bounded output and cancellation.

Build emits source/contract/artifact digests and a validation result tied to the exact content. Any edit invalidates that result. Try uses independent fixture data and no live connector grants by default. Use this activates the reviewed digest, asks for any missing capabilities, and chooses a unique slug. Grant changes cannot be smuggled in by changing the manifest after review.

Change app copies installed source to a draft and preserves its origin version/customized status. Activation compares the original installed digest to detect conflicting builders. Stop/drain the active app, make a stopped-data snapshot if the update can migrate data, stage a replacement package, then publish it with an activation journal in feature metadata. The app owns migrations. Record phases `prepared`, `switching`, `checking`, `active` or `failed`. On a crash or readiness failure, preserve both packages and the snapshot and disable the instance with a repair action. Do not silently run old code against possibly migrated data. This small interruption journal is required data protection, not an automatic rollback system.

Archive immediately rejects new calls, revokes active runtime/view credentials, cancels schedules and pending approvals, drains/stops owned processes, and preserves package/data. Reactivation requires grants to be reviewed and new runtime credentials. A separate, explicit Delete data removes preserved records only after stopping writers. A package export is not a personal backup. Whole-Home backups currently use an explicit directory allowlist in `src/lib/home/backup.ts`, so adding folders alone does not preserve apps. Add `apps` and `app-drafts` through a stopped-app snapshot adapter, exclude regenerable dependencies/cache/logs, include feature metadata, and revoke credentials/disable jobs on restore pending review. The backup process asks the running Home to quiesce apps before copying and resumes its prior enabled instances afterward. If quiescence is unavailable, report app data as omitted/incomplete in the manifest and UI, never as a complete backup. A stopped Home can be copied after verifying no owned writers. Do not copy only an open SQLite main file.

Disabled flag means unavailable app routes/procedures/tools and no metadata initialization, processes, scheduler participant, or app credentials. The flag is startup-scoped. Shutdown/restart cleans up work from a prior enabled process. Existing app data may remain untouched. Removal does not delete deliberately created Ri tasks/notes or undo external effects.
