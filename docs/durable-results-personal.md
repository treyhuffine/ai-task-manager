# Durable results: personal integration

The personal-home expansion requested after the original pilot is implemented and exercised through isolated real-runtime and browser trials. The [task specification](durable-results-spec.md) remains the design source. The [historical pilot record](durable-results-pilot.md) preserves the original code and non-code trial, including its omissions and portability limitations. Its original checks do not claim to verify this expansion.

Current internal storage uses `work_results`, `work_result_tasks`, `work_result_decisions`, and `work_result_ai_reviews`, with matching `workResults`, `workResultTasks`, `workResultDecisions`, and `workResultAiReviews` schema exports and schema-derived `WorkResult*` types. The forward `drizzle/0006_work_result_names.sql` naming migration preserves existing data, rowids, and foreign keys, and leaves historical migrations `0002` through `0005` unchanged. Decisions are human, agent, or system dispositions, distinct from AI review requests and reports. The public result actions and `/results` and `/api/results` routes remain stable. The earlier verification and trial records below predate this internal naming migration. The final naming migration verification section records the current checks.

A handoff remains an immutable Markdown snapshot with retained files, links, producing context, exact task membership, human decisions and independent-review evidence. Ordinary conversation is unchanged. Reporting and AI review do not accept work or complete tasks. The optional automatic policy requests one review after a substantive saved result, and explicit Accept and complete composes acceptance with the existing task lifecycle.

## Personal surfaces

Saved results is one filterable list at `/results`, reached from the existing menu and command palette. It searches saved titles and content, filters stored task or execution membership, pages results and optionally includes superseded snapshots. Exact links still open `/results/:id`. AI reports remain nested under their target rather than appearing as duplicate primary deliverables. Taskless results remain discoverable after the producing conversation is pruned.

The task slideout renders a Results section outside the editable document. It hides when empty, reads existing saved records, shows current snapshots and can expand history. Task membership comes from the result's saved links rather than an execution's current task associations. Task content chats save against their exact producing task when task IDs are omitted. Explicit `taskIds: []` remains taskless. Notes continue to use their existing AI chat and ordinary result links.

Execution headers expose a Results shortcut to the same filtered collection on desktop and mobile. It stays available for retained results after handoffs are disabled. Current conversations, task content chats and note content chats use the shared transcript renderer for saved result events. Hiding creation or collection entry points does not disable retained exact pages, inline cards, attachments or reviewer attention.

The implementation lives in `src/app/results`, `src/components/results/result-list.tsx`, `task-results.tsx`, `execution-results-shortcut.tsx`, the existing task slideout and execution header, `src/hooks/use-results.ts`, and the existing menu/command definitions. Collection reads use the shared query facade and saved-result authority checks. No separate result search index or copied task/note body is introduced.

Live GitHub checks are shown separately from the agent's saved answer. The existing PR observation requests `headRefOid` alongside its check rollup. Results bind that live status only when its full head SHA equals the handoff's known clean commit. The panel shows the commit and observation time, and keeps dirty, missing, changed or unavailable targets unknown. It does not copy current PR status into immutable evidence or imply that checks covered an unbound working copy. Closed and merged PRs retain the existing unavailable-check behavior. Parser, API and renderer tests cover this boundary.

## Agent reviewer preferences

Migration `0005_public_the_renegades.sql` adds two nullable columns to `workspaces`: `review_before_handoff` and typed JSON `review_defaults`. Neither has a database default. Null automatic-review preference resolves off. Null or omitted reviewer fields inherit. `WorkspaceReviewDefaults` is derived from the Drizzle record, and the shared workspace creator and updater validate the preference shape.

The resolved reviewer follows a one-off request override, then the associated producing agent's review defaults, then normal defaults. Harness resolution precedes the model, variant and effort. Settings from another harness or another selected model do not form a mixed tuple. An unavailable saved model, effort or variant remains visible and cannot silently launch a different choice. Explicit provider-default overrides can clear inherited variant or effort settings. The resolved tuple is saved before dispatch, and identical request-key retries retain it after defaults change or capabilities are disabled.

Association is derived only from an authorized producing session or execution. A linked task does not implicitly select an unrelated agent. Taskless results use their producing agent when one exists. A result with no associated agent uses normal defaults and its request override and has no Use for this agent action. A retained producing execution can preserve this association after its conversation is pruned.

Changing the picker edits only the request. Use for this agent and Reset agent reviewer explicitly persist the producing agent's preference. The existing agent settings form edits the same fields and offers Review before handoff independently of the reviewer choice. Saving preferences does not enable the home capabilities. Signed harness sessions cannot write these preference fields through the settings API. The normal authoring model and global defaults remain unchanged.

`src/lib/work-results/reviewer-preferences.ts` owns source association. `reviewer-selection-defaults.ts` supplies the same coherent inheritance to the server and picker. The workspace query layer owns validation and persistence. `src/components/results/reviewer-selection.tsx` and `src/components/agents/agent-setup.tsx` expose the explicit controls. Workspace mutations optimistically merge preferences into the existing workspace and result-detail caches and roll back failures.

## Automatic review and runtime boundaries

Current [Handoff and review preferences](work-result-guidance.md) from Settings, General and Agent setup are loaded when preparing or reporting a handoff and captured in independent review assignments. The current request takes precedence over agent preferences, which take precedence over shared preferences. They do not enable result capabilities, accept work, complete tasks, or override a reviewer's assigned target and read-only restrictions. The trial evidence below predates this scoped-preferences integration, whose migration generation is deferred.

Both home capabilities must be enabled and the producing agent must explicitly set Review before handoff. Saving a primary result records one automatic request in the same database transaction, after recording any included independent-review evidence. One result linked to multiple tasks produces one request. Off or null preferences produce none. Already compatible independent evidence can satisfy the policy, while implementer-reported independence and incompatible scope cannot gain stronger claims through reuse.

The handoff is immediately readable while its review is queued, running, failed or cancelled. The saved request retains the original brief, exact target, resolved reviewer tuple, scope, file manifests and automatic-policy provenance. Unavailable reviewer settings or original inputs produce visible failed outcomes without discarding the usable handoff. Reviewer observations remain distinct from the saved requested revision.

`src/lib/work-results/automatic.ts` reserves policy requests and binds eligible work through the same dedicated reviewer context used by manual requests in `runtime.ts`. The server waits for the producing context to be quiescent before inspecting its active working copy. Final provider admission and submission recheck the durable request and source lifecycle. Source changes while discovery or setup yields cannot silently retarget the reviewer. Existing executor lifecycle hooks drain eligible queues rather than introducing another scheduler or workflow engine.

Dispatch uses existing server-owned sessions, chat events, runs, permissions, API concurrency leases and budgets. It creates no new primary task or execution. The installed adapters expose no supported native independent-review API, so the implementation uses fresh read-only contexts and retains that limitation. It never sends an assumed native review command. Requested effort is not proof that the provider applied it. Dirty working copies without an exact checkpoint and mutable links remain qualified rather than being presented as fresh exact evidence.

Dedicated reviewer sessions stay out of ordinary chat, execution, unread and primary-conversation queries. Questions, permission decisions, available activity, errors and Cancel remain accessible from the exact target and existing desktop/mobile attention surfaces. A reviewer may inspect its assigned target and report findings, but cannot mutate ordinary authoring settings, escape read-only permissions, create another primary result or launch another review. Reports do not trigger review-before-handoff, and Address findings remains explicit contextual feedback rather than an automatic repair loop.

Turning off either home capability durably cancels queued preparation and review operations. Turning off an agent's automatic-review preference immediately cancels its queued automatic requests and bound queued runs. Changing reviewer defaults alone does not alter an existing assignment. Re-enabling does not resume retired requests. Admitted work may finish its exact authorized assignment or be cancelled. Cancelling preparation never stops the authoring conversation, and previously sent human feedback retains its ordinary delivery.

Boot recovery runs before generic session reconciliation. Interrupted work becomes a visible terminal outcome instead of a blind replay. A deliberate retry creates a new review attempt for the same exact target. Retained reports, scope, brief, provenance and terminal outcomes survive internal-session/run pruning. Attachment retention includes saved galleries, feedback uploads, review manifests and feature run payloads, and remains active with both capabilities off.

## Explicit acceptance and task completion

Accept still records only a result decision. Accept and complete is a separate human action against one exact current handoff and an eligible task from its saved membership. Multiple eligible tasks require an explicit choice. The server rejects a successor, known code mismatch, stale task revision, invalid task selection or unmet child/runtime acknowledgments before committing either acceptance or completion.

The action reuses the existing task lifecycle, recurrence, history, open-child and running-workstream controls. Acceptance and completion commit in one immediate transaction and roll back together. Runtime coordination is followed by fresh revision and database checks. Committed retries replay the original outcome before gates and source availability checks, and the client preserves uncertain submissions rather than turning a retry into another recurring occurrence. Unknown code identity is shown as unknown, not certified fresh.

The service is `src/lib/work-results/completion.ts` with query-layer composition in `completion-queries.ts`, exposed through the normal query facade and `POST /api/results/:id/complete`. `result-completion-action.tsx` supplies task selection and the existing lifecycle acknowledgment flow. See [Accept and complete](durable-results-completion.md) for the exact API contract and recovery rules.

## Expanded real-runtime trial

The isolated automatic-review trial used a real Codex author in an existing execution and an explicit producing-agent preference of Codex, `gpt-5.5`, high effort. The author returned a six-bullet calculator handoff checklist as ordinary conversation. Human Save retained its exact content, with no task membership, and atomically created one automatic review request. Immediate identical Save replay returned the same primary ID and did not create another review. Dispatch began after the author's runtime was quiet.

The fresh read-only reviewer saved an assigned report through the strict host completion transport in approximately 65 seconds. Primary result `cf769613-b8b1-83c6-a90e-7fe5b6945ff9`, review `fa961ffc-7200-8dda-895b-7bc6aed131f3`, and report `0f881f3b-6d65-8dbd-9155-26677bf22f7a` remain in the isolated trial home. Requested model and effort are retained, while provider-observed model and effort remain unknown. Its observed dirty working tree remains unbound rather than gaining exact freshness.

The report found no actionable issue in the checklist text but also raised an unrelated preexisting calculator file as a possible no-change violation. That attribution was unsupported by the available timing and ownership evidence. The shared method now explicitly requires evidence connecting preexisting or unrelated files to the producing work before making that claim. This trial supports the transport and lifecycle, and also shows why a saved AI report remains review evidence rather than an automatic decision.

Resetting the agent preferences to null and disabling both home capabilities preserved the primary, report and filtered list. An identical Save retry still replayed the committed result, with exactly one completed review and zero acceptance decisions. Viewing the disabled exact page and review details at 1280 and 390 pixels created no further review, showed the retained report and unknown live GitHub status, and produced no page errors or horizontal overflow. There was no linked PR in this isolated repository, so actual passing GitHub checks were not claimed. Exact clean-SHA binding is covered by API/parser/component fixtures.

## Privacy and removal boundary

This implementation is personal. Linking a result to a task never publishes its files, private review evidence, original brief or runtime trace. Team publication and team reviewer routing await a homes/team authority model and an authorized shared runtime. They cannot be implemented by copying a personal result into an arbitrary task or invoking a member's personal agent.

The capability switches are operational rollback, not migration rollback. The existing preservation, authenticated export and deliberate removal steps in the historical pilot document remain applicable. Keep result readers, old event rendering and attachment ownership until saved work has been preserved or migrated. Do not remove tables or referenced files because automatic review is disabled.
