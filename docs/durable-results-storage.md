# Durable result storage and admission checks

This records the implemented storage boundary of the opt-in pilot in [the specification](durable-results-spec.md). It distinguishes automated verification from the separate real-harness and device trial.

The four tables are `work_results`, `work_result_tasks`, `work_result_decisions`, and `work_result_ai_reviews`. Their Drizzle exports are `workResults`, `workResultTasks`, `workResultDecisions`, and `workResultAiReviews`. `WorkResultRecord`, `WorkResultTaskRecord`, `WorkResultDecisionRecord`, and `WorkResultAiReviewRecord` in `src/db/types.ts` derive from those schema exports. Supporting `WorkResultActor`, `WorkResultDetail`, and `WorkResult*` JSON types use the same domain names. Every table uses the shared timestamp definitions. Snapshot content, saved task membership, and dispositions are append-only. Nullable provenance references can disappear when their source chat, event, execution, or run is pruned. Saved snapshots, review briefs, reports, decisions, and attachment ownership remain.

`work_result_decisions` is the renamed `result_reviews` table. It stores attributed human, agent, or system dispositions such as acceptance, dismissal, and contextual feedback. Independent AI review requests and evidence remain in `work_result_ai_reviews`. This distinction makes the internal names describe their roles without changing the saved meaning of either record.

Feature queries live in `src/lib/work-results/queries.ts` and are reexported by `src/lib/db/queries.ts`, including `getWorkResult`, `createWorkResult`, `listWorkResults`, `createWorkResultDecision`, and `createWorkResultAiReview`. Runtime database helpers live in `src/lib/db/work-result-runtime-queries.ts`.

Integration preserves main's entire released migration history, `0000_typical_shockwave` through `0009_linked_folder_read_only`. The feature branch independently used different migrations numbered 0002 through 0006. Those conflicting files, snapshots, and journal entries are excluded from the squash. They remain historical development evidence in that branch, and are not an upgrade path for released homes. The release migration `0010_many_captain_universe`, generated once the implementation was on main, creates the four tables and adds the reviewer preference and workflow guidance columns (`user_state.work_result_guidance`, `workspaces.work_result_guidance`, `workspaces.review_before_handoff`, and `workspaces.review_defaults`), all nullable with no default. It contains only `CREATE TABLE`, `CREATE INDEX`, and nullable `ADD COLUMN` statements, so no existing table is rebuilt and every rowid and FTS index stays intact. A home applies it the next time its server starts.

Vitest builds these tables from the release history like any home. `work-result-migration.test.ts` upgrades a populated 0009 database through 0010 and checks that existing rows, rowids, and links are unchanged and that the four preferences arrive null. It also covers the 15 foreign keys and their SET NULL, CASCADE, and RESTRICT behavior, every unique and check guard, the 14 indexes, a fresh home, and a second run that applies nothing. Deleting a session's `chat_events` checks `work_results.source_event_id` once per event, so `idx_work_results_source_event` keeps each check a keyed search, and the test pins that plan. The test-only fixture that stood in for the migration before generation (`src/test/pending-schema.ts` and `src/test/work-result-schema.sql`) is retired. Its tables, columns, defaults, foreign keys, indexes, and checks matched 0010 apart from that index. A development home that applied the separate feature lineage needs a deliberate data-preserving reconciliation before it can join main's history, with any real data change authorized separately.

The internal naming change preserves the public `report_result`, `get_result`, `list_results`, `request_result_review`, and `report_result_review` actions and the `/results` and `/api/results` paths. Request-key namespaces, wire IDs, response fields, and client cache keys remain stable. For compatibility, `WorkResultDetail.reviews` and a decision response's `review` field keep their existing names. Historical pilot and expansion verification describe the earlier names and do not establish verification of the naming migration.

The current branch provides one local personal authority. Trusted human requests use that established owner. Agent requests use the existing signed Ri session identity. Results do not introduce homes, memberships, team publication, or private-to-team routing. The integration keeps main's existing home and device authority, placement, and transfer boundaries. It does not add team publication or private-to-team routing.

The automated suites are in `src/lib/work-results/queries.test.ts`, `src/lib/orchestrator/result-actions.test.ts`, and the runtime, capability, instruction, presentation, fixture, and attachment suites. The storage suite uses real isolated SQLite databases and attachment files. It mocks unrelated asynchronous embedding calls so they cannot outlive the temporary database. Recorded runs in the pilot and personal integration documents are historical evidence from before the internal naming migration.

Real code and non-code production, useful independent findings, natural omission and over-reporting behavior, native adapter availability, mobile inspection, and the enabled-to-disabled running-device trial require the actual pilot notes. Passing storage tests alone does not establish those outcomes. No existing exploratory checklist is silently converted into an implementation claim.

## Retention integration and deliberate removal

The retention integration is one named function, `getAllWorkResultAttachmentFileNames`, called by the existing attachment GC collector. It includes result files, disposition files even without a feedback destination, scope evidence, and the complete prepared message attachments retained on feature-tagged ordinary runs. This function continues operating with both capabilities disabled.

Operational rollback disables the capabilities in the current application version. It does not remove migrations, tables, immutable records, ordinary feedback delivery, or attachment roots.

Actual code removal is a separate cleanup. Stop new feature dispatch and finish or cancel admitted operations. Preserve the four tables and their read and retention support until saved snapshots, nested reports, dispositions, provenance, exact task links, and referenced files have a usable authorized export or have been migrated into supported existing content. Handle old `work_result` transcript references before removing their renderer. Remove the query facade exports, retention integration, actions, instruction delivery, runtime integrations, and UI integrations together. Any destructive data deletion needs a separate explicit decision.
