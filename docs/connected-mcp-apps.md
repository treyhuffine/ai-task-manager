# Connected MCP apps

Connected MCP interfaces use the same account and integration engine as their tools. There is no second installation, copied account, synthetic Ri package, or separate demo server. Settings → Plugins retains its existing UI.

## User experience

Chat is where a connected service is used. Only real application UI makes it an app you open: a screen that opens on its own.

- A connection whose server offers an interface, a standalone screen or a tool whose result renders, appears once in the Apps library. It can be found under Apps or Connectors. Tools-only connections retain their current management and chat paths.
- Only a service with a standalone screen (below) gets rows in the rail's Apps flyout and Open <name> commands in ⌘K, while one of its accounts can open it, beside installed apps (`docs/rail.md`). Each standalone screen is its own row, titled and marked as OpenAI's spec renders an entrypoint: the tool's `title`, then `annotations.title`, then `name`, and the tool's icon, else the server's (`serverInfo.icons`), else the catalog logo or a generic mark. ⌘K also finds a screen by its service's name. On the service's page, its first row is the one lit. A service whose interface only comes back as a tool result, such as Todoist's task list, has neither. It is used from chat with `@` and stays in the library and Connectors.
- `/apps/~connected/<server-id>` shows the service and exact account, connection management, Try in chat, and the recent results it can reopen. It has no tool forms, since the agent chooses tools and inputs in chat. Try in chat opens the main chat with the service's chip and a starter prompt written after it, ready to send, as ChatGPT's Try fills "@Todoist What's on my list today". Official catalog entries may carry a curated prompt (`starterPrompt` in `integration-meta.ts`: Todoist "What's on my list today?", MagicPath its manifest's first prompt). Anything else gets "What can you do with <name>?". Nothing is sent and no access changes. A Home with mentions off gets the prompt alone.
- Open app appears only for a standalone screen. It calls that entrypoint with `{}` through the ordinary approval gate, with no input form, and the returned view fills the app page full screen. Choosing the app in the rail's Apps flyout or ⌘K (`?open=<entrypoint>`) opens the screen the same way. Once open, the URL names the screen (`?screen=<capture>`), so a refresh reopens it without calling the entrypoint again, and the page lists it under recent results to reopen full screen. Opening a screen that is already open returns to it (see Instances), and Reload in its header starts it over with a new call. An entrypoint that rejects `{}` shows its error plainly, with Try again as a new request. Leaving while it opens cancels it. A tool name such as `home` does not imply a launcher, and no other tool runs from the page.
- A completed, authorized model tool call can add an interactive result to its chat. Expanding it beside the conversation moves the live iframe with `moveBefore` where supported, retaining the guest's state and the chat draft. Older browsers fall back to remounting the captured result. Opening, refreshing, or expanding never reruns the original model tool call.
- UI operations use the existing approval system. The native card identifies the proposed operation. Allow once retries the same invocation, while Decline does not execute it. Closing a view or leaving a workflow cancels its pending requests and unused approval grants, including approval responses that arrive late. An operation already admitted to execution may finish. App approvals do not wake the agent to repeat the operation.
- An app's message (`ui/message`) sends only while the person is working in that app, and is otherwise left as a draft (see Model context and messages). The most recently updated live view can attach its acknowledged model context to the next human send in that exact chat, and the composer shows what it attached. Sending during the first context update waits for its acknowledgement before attaching the revision. A source mention identifies the account separately from selected view data. Context remains untrusted app data and confers no permissions.
- A source chip's Open <service> opens its latest live result beside that chat, or the account's Apps page when no result exists. Existing harness and account restrictions remain in force.

Connected views are enabled by default. `RI_MCP_APPS=0` disables them independently of `RI_LOCAL_APPS`. Mentions are always on. This supersedes the earlier opt-in rollout in the mentions spec. Discovery uses cached metadata. Existing servers need their usual discovery refresh after upgrading to preserve newly supported metadata aliases. Production is not restarted by implementation or tests.

## Supported interfaces

The initial profile accepts self-contained HTML with inline scripts and embedded assets. It supports standard `_meta.ui.resourceUri` (and `ui/resourceUri`), `text/html;profile=mcp-app`, tool visibility, authenticated `resources/read`, ordinary MCP results, `tools/call`, model-context updates, text chat suggestions, HTTPS links, height changes, and inline/expanded display.

A standalone screen is a global entrypoint: a tool whose `_meta["openai/ui"].entrypoints` includes `{ "type": "global" }`. It is documented as the "Sidebar apps" extension in OpenAI's plugin docs and its [MCP extensions spec](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md#global-entrypoint): ChatGPT lists it in the sidebar and opens it full screen, the server must accept `{}` as its arguments, and `ui.visibility` is ignored when it opens. So an app-only launcher counts, and runs with whichever tool audience its visibility admits. Thread entrypoints open as a tab beside a chat and file entrypoints open a file (see Entrypoints and instances, and Files). Neither is a standalone screen. A UI resource's `availableDisplayModes` and `preferredDisplayMode` choose where a result first shows and which modes the view may ask for (see Display modes).

The compatibility adapter recognizes `openai/outputTemplate`, `text/html+skybridge`, `openai/widgetAccessible`, and `openai/ui` entrypoints. It supplies `window.openai` tool input, output, private tool-response metadata, theme, widget state, tool calls, draft suggestions, display requests, and external links through the same bridge. The OpenAI MCP extensions an app reaches through `@openai/mcp-extensions` (Bits & Bolts is one) are covered extension by extension in the compatibility table below.

Interfaces requiring external scripts, network domains, or undeclared capabilities receive an explicit unsupported explanation. A declared dedicated origin alone (`ui.domain`, or ChatGPT's `openai/widgetDomain`) does not: the MCP Apps spec makes its format host-specific and ties it to network uses (OAuth callbacks, CORS, API key allowlists) that the declared domains already rule out, so the view renders on Ri's own sandbox origin under the restrictive CSP. Requested permissions (`ui.permissions`: camera, microphone, geolocation, clipboard write) do not either. The spec has apps not assume them and lets the host decline, so Ri renders the view and grants none. Todoist's task list declares ChatGPT's domain, and Microsoft Flint's chart asks for clipboard write. Both were refused until October 19. Excalidraw loads its code from esm.sh, so it still shows the explanation with its text result.

An inline view is exactly as tall as it reports with `ui/notifications/size-changed`, which the host clamps to 160 to 900 px, and it starts at 420 px until the first report. It is capped at 80% of the window, and the view scrolls inside only past that. Until October 19 a flex rule collapsed every inline view to 240 px, which cut off the end of Todoist's list. `view-size.browser.test.ts` pins the height with the real component and CSS. On an app page, an open result carries Close in its own header row. A full-screen screen titled the same as its app shows no title row, since the page header already names it. Their tools and text results remain usable. A view may download files it names (`ui/download-file`), read its own server's resources (`resources/read`), and use the file it was opened for (Files). It cannot browse resources Ri did not give it, and there is no picture-in-picture.

A view runs in an opaque, sandboxed frame with this CSP: its own inline scripts by hash, no network (`connect-src 'none'`), images and fonts only from `data:` and `blob:`, no frames, and `form-action 'none'`. Within that it may compile WebAssembly and start workers from `blob:` URLs it builds, as Bits & Bolts' STEP importer does, and a worker inherits the policy. The frame allows forms, so an app's submit handlers run (Bits & Bolts' Create part is a plain form). A guard Ri puts first in every view cancels any submission the app left alone and makes `form.submit()` do nothing, so no form navigates the frame, and the CSP would block the request anyway (`host.browser.test.ts`). Total Finance's actual service is not qualified by the synthetic calculator fixtures. Its advertised resource must be checked against this profile after the owner restarts or refreshes their server.

## Implementation and authority

- `packages/mcp-apps-host` contains the shared `AppBridge`, opaque relay, CSP, and browser lifecycle. `packages/app-kit` re-exports it and inlines it at build time, so the packed SDK never depends on this workspace-only package. The connected adapter has no local builder, app-kit, or domain dependency.
- The integration engine's trusted `prepareMcpResult` hook binds the resolved connection, caller, attempt, redacted original input, and current authority before dispatch. Its returned observer receives the original MCP result after successful execution and rechecks that bound authority. A late result cannot inherit replacement credentials, capabilities or tool permissions. Capture failure cannot turn a completed operation into a retryable failure. Private `_meta` is absent from model results and audit previews.
- `lib/mcp-apps/service.ts` discovers capabilities, binds captures to exact accounts and chats, reads only the declared UI resource on that account, and dispatches UI calls through `runAction` with app audience. Every operation checks current account status, credentials/capability revision, tool overrides, and chat access before execution and before releasing results. Viewer procedures also recheck the signed-in key before and after work.
- The transcript stores only a native `mcp_app_result` event and opaque capture ID. HTML and private results remain in Home-owned `processState`. Captures and view sessions expire after 30 minutes or restart. Expiration leaves the original text intact and asks for a new result. It does not replay an old call.
- Native launch preparation creates a server-owned view and invocation before any effect. Retries of an expired, evicted, or unknown launch fail instead of creating another invocation. Within a view, identical in-flight deliveries coalesce. Completed or uncertain failures are never replayed. Only a pre-effect approval pause permits a retry of the same input and identity.
- Cancellation is bound to the exact viewer, view and invocation. Bounded cancellation receipts reject delayed first deliveries and approved retries. Cleanup remains available after provider access changes, clears only the matching pending approval and unused grant, and also runs when an in-flight request creates an approval after cancellation. Browser cancellation is best-effort if its connection to the Home is lost.
- Limits: 32 captures and 32 view sessions, 2000 operations per view, 64 KiB input, and 12 MiB prepared HTML. A captured result is at most 512 KiB. An app operation's result may be up to 24 MiB (Bits & Bolts reads model files of about 6 MB) and a view may receive 512 MiB in all. Results of 512 KiB or less are kept, 8 MiB per view, so a duplicate delivery gets the same answer, and a larger one is delivered once and its duplicate refused rather than run again. Context is capped at 768 KiB per update and 10 updates per second. A view's messages may be 16 MiB (a file it saves), the host's to it 64 MiB, and either side 100 per second.
- Ri's MCP endpoints report progress every 20 seconds while a tool call is in flight, when the client gave a `progressToken` (`withProgressKeepalive` in `src/lib/mcp/http-server.ts`). Claude Code drops an MCP request after 60 seconds without progress, so a call that waits on a person, a server's form above all, would otherwise end before the answer.
- Frozen context is stored only on an accepted human message and reauthorized on dispatch and recovery. Local authoritative app context and remote untrusted context remain separate fields.

## Entrypoints and instances

OpenAI's [entrypoints](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md#mcp-app-entrypoints) are tools a person opens rather than the model, declared in `_meta["openai/ui"].entrypoints` on a tool with a UI resource (`viewMetadata` in `lib/mcp-apps/metadata.ts`). Every launch goes through `prepareConnectedLaunch` and the ordinary approval gate, with a kind:

- `global`: a standalone screen, opened full screen on the app's page with `{}` (above).
- `thread`: a tab beside a chat. The composer's app button lists the tabs a chat may open (`connectedApps.chatTabs`), next to local apps: only accounts that chat's agent may use, by the same check every view's authority makes. A tab opens with `{}` in the pane beside the chat, as one instance per chat, and Reload in the pane starts it over.
- `file`: the viewer for the extensions it lists (Files, below).
- `settings` and `preview`: an app a settings button or a form option names. These are not OpenAI entrypoints, only the same launch path.

Instances. The spec gives each thread its own instance and says no more about reuse, and [openai/mcp-extensions issue 54](https://github.com/openai/mcp-extensions/issues/54) asks whether a model's later call should reuse an open entrypoint app. It is unanswered. Ri's reading, pinned in `service.test.ts`:

- An entrypoint keeps one live instance: a thread tab per chat and person, and a global screen per person. Opening it again returns to that instance without calling the tool. `fresh` (Reload) starts over.
- A model's tool call never reuses an entrypoint instance. Its result shows in its chat on its own, as ChatGPT behaves today. Sharing a `ui.resourceUri` changes nothing. An app that wants its open instance to reflect a model's work does so through its own server's state, which every instance reads.
- An instance lives as long as any view: 30 minutes, or until the Home restarts.

## Deep links

OpenAI's [deep links](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md#deep-links) open a global screen at an app-relative URL. Ri's form of the link is its own app URL: `/apps/~connected/<server-id>?open=<tool>&path=<encoded app-relative URL>`. The path must start with one `/`, carry no fragment and fit in 2 KiB (`normalizeDeepLink`).

- A new screen receives it in `hostContext["openai/deepLink"]` at initialization.
- A screen that is already open is moved in place: Ri sends `ui/notifications/host-context-changed` with the new `openai/deepLink` to the live view and records it, so a remount opens at the same place. The URL keeps `path` beside `screen`, so a refresh does too.
- OpenAI's `codex://` and `chatgpt://` schemes and plugin IDs belong to ChatGPT. Ri has no plugin directory, so it reads only its own link.

## Display modes

A UI resource's content item may carry OpenAI's `_meta["openai/ui"].availableDisplayModes` and `preferredDisplayMode` ([Display Modes](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md#display-modes)). Ri shows views inline and full screen, which in a chat means the pane beside it, and has no picture-in-picture.

- A model's result opens as ChatGPT opens it: the preferred mode, else full screen when both are declared, else inline when nothing is declared (`initialDisplayMode`). A full-screen result opens beside its chat when it arrives, if the pane is empty or holds another result that opened there the same way, which goes back into the transcript with its view intact. A tab, or a result the person moved beside the chat, stays: the new result offers Open beside chat instead, so replacing it is the person's choice (`mayPlaceResult`). Scrolling back never moves one again.
- A resource that declares only inline has no Open beside chat, and one that declares only full screen never shows inline. A view's `ui/request-display-mode` for a mode its resource did not declare is refused.
- Entrypoints always open full screen, as ChatGPT does: a global screen on its page, a tab or a file beside a chat.

## Model context and messages

OpenAI's [model context](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md#uiupdate-model-context-extensions) and [message](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md#uimessage-extensions) extensions are advertised (`openai/modelContext`, `openai/message`) to every connected view that can honor them.

- `ui/update-model-context` replaces what that view attached before and is answered with `_meta["openai/modelContext"].updateId`, renewed only when the content or structured content changes. Text, images, resource links, embedded resources and structured content are accepted, 768 KiB per update. Audio is refused, as the spec lists it unsupported.
- The composer shows each app's context as one chip: titled items (`openai/title`), text thumbnails (`openai/thumbnail`), images, links and embedded resources. Blocks marked `annotations.audience: ["assistant"]` are hidden from the person and still sent. Removing the chip drops the whole group, as the spec describes for desktop, and the view receives `openai/modelContext: null`. A remounted view receives what it still has attached in `hostContext["openai/modelContext"]`.
- A global screen has no chat of its own, so its context goes with whichever chat its person sends next, when that chat may use the screen's account: any chat without an agent, and an agent's chat when its agent may use the account. Sending binds the context to that chat's authority, which every dispatch checks again. A chat that may not use the account refuses the send before the message is saved, naming the app, and the person can remove its context and send.
- The model never sees block `_meta`. Images and embedded binary resources are saved as attachments when a message freezes the context, and the agent gets `[[file:...]]` markers that become paths, so no image bytes sit in the transcript.
- `ui/message` takes OpenAI's `_meta["openai/message"]` with the spec's defaults (`target: "active"`, `send: true`). Untitled text becomes draft text. Titled text becomes one chip in the composer, removed as a unit. Images and blobs become attachment chips, a resource link becomes its title and URI, and an embedded text resource becomes a titled chip.
- `active` is the view's chat, or the main chat for a view without one. `new` starts a new chat on the same surface: a new main chat, a new chat for the same agent, or a new chat in the same execution.
- `send: true` sends only when the person's own input in that view led to it: the browser's transient user activation in the view's frame, from a click or key press in the last few seconds. The view's relay frame reads it as it forwards each request (`navigator.userActivation`), and the app cannot set it. Focus is not input, so an app that focuses itself, sends as it loads, or sends later on a timer leaves a draft instead, and the view says so quietly. An app may send once every 3 seconds and 30 times per view. A sent message records its app (`raw.sentByApp`), the transcript shows From <app>, and the agent reads it as a message the app sent on the person's behalf. It grants nothing. `send: false` always leaves a draft.

## Forms

A server may ask the person to fill a form while a tool runs: MCP's form elicitation and OpenAI's [extended forms](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md#openai-form-elicitation) (`lib/mcp-apps/elicitation.ts`, `form-schema.ts`, `components/mcp-apps/form/`).

- Every MCP connection Ri opens advertises `elicitation.form` and `extensions["openai/elicitation"].form`. On 2026-07-28, a form arrives as an `input_required` round, with its schema in `_meta["openai/elicitation"].requestedSchema`, and `callTool` answers each round itself. On older connections it arrives as `openai/elicitation/create` or `elicitation/create`.
- A form goes to whoever caused the call. The engine gives every call its run (`callOrigin`), so a model's call shows the form as a card in that chat, and an app's own call shows it over that app view. A 2026-07-28 round is matched exactly. A 2025-era request on the call's own HTTP stream is matched through the call's async context. A local process has no tie to a call on the wire, so it gets the run only while exactly one request is in flight. A form Ri cannot place is refused and never shown to someone else.
- Fields follow OpenAI's SDK shapes: text with `pattern` and suggestions (`x-openai-suggestions`, on strings and on array items), enums and titled options with descriptions, image grids once any option has `x-openai-thumbnail` (the others get a fallback image), multi-selects, free-form lists, switches, and bounded numbers. Answers are validated with `@cfworker/json-schema`, the validator OpenAI's SDK uses. A form with any field Ri cannot render is reported as unsupported and never partly shown.
- Resource selection (`x-openai-input`, type `resource`, or its alias `file`) covers single and multiple choice, explicit and implicit selection, option thumbnails and previews. As the spec says, implicit selection always lets the person add their own, and without `userOptions` that is any file. Explicit selection without `userOptions` takes only its options. A `resource_link` preview reads from the asking server. An `mcp_app_tool` preview opens that app through the approval gate. Defaults may name only supplied options.
- A person may add their own files only for a server on this computer, a loopback URL or a local process, for which a `file://` URI means something: a chat attachment, an upload, or a file or folder inside the chat's agent folders. A remote server gets only its own options, as ChatGPT's web app offers.
- A 2025-era form holds the server's call open, so it expires after 9 minutes, inside Ri's 10-minute inactivity limit. A 2026-07-28 round holds nothing open and may wait 25 minutes. Each place holds four open forms at most. The transcript records how each form ended (`mcp_form_response`) with the app's name, the outcome and the reason a form could not show, and keeps exactly those through a reload or a restart (`toChatEventDTO`).

## Settings

A server that publishes OpenAI's [structured settings](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md#structured-settings) (`capabilities.extensions["openai/settings"]`, with `readTool` and `updateTool`) gets a Settings section on its connection page: Settings, Plugins, MCP servers for a server you added, and on each account of a catalog provider. Ri asks the server only when its recorded capabilities name settings and its account is connected and on.

- The read tool runs with `{}` and returns a schema, a value for every setting and an optional layout. Ri draws booleans as switches, string enums as choices, and text, numbers and whole numbers as fields that check `minLength`, `maxLength`, `pattern`, `minimum`, `maximum` and `multipleOf` before anything is sent. Groups appear in the server's order, and settings the layout leaves out follow in Other settings (Settings when there is no layout). A setting of another kind, or one without a valid value, shows why instead of a control. A layout naming an unknown setting, or one setting twice, fails the read, as OpenAI's SDK does.
- A switch or a choice saves as it changes, and text or a number on blur or Enter. Ri reads the current schema first, checks the value against it, and sends only the settings that differ (`{"set": {...}}`). The values the server returns replace the page's. A refused change goes back to the saved value with the server's reason.
- A tool button is titled by the tool (`title`, then `annotations.title`, then `name`). A plain tool runs with `{}` and its text shows beside the button. A tool with an interface opens it in a dialog, launched as a `settings` view through the ordinary approval gate. Only buttons the current layout names run.
- The person changing a setting, or clicking a settings button, is the approval, as with the email composer's Send. These calls carry `mcpSettingsCaller(actionId)`, stamped only by the owner-viewer procedures in `lib/mcp-apps/settings.ts` and bound to that one action, and the approval policy lets exactly that action through. A tool turned off in the server's tool list stays off here too.

## @ search

A server can offer its own items in the composer's @ menu, OpenAI's [composer at-mentions](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md#composer-at-mentions): Bits & Bolts offers the parts in its library. It advertises `openai/mentions` with a `searchTool`, or the deprecated `_meta["openai/extensions"]["mentions/search"]` marker on a tool when the capability is absent.

- Ri asks every such server the chat may use, in parallel, with `{query}` as the app, on the server's exact account. Workspace scopes and account pins apply as they do to a chat's other app use. Each server has three seconds, so a slow one only leaves its group out. The mixed picker asks once something is typed and shows up to five items per app. `@app:` asks even for an empty query, as the spec allows, and shows every item the app returned, at most 20. Typing is debounced and recent answers are reused for a few seconds.
- A server is skipped, with its reason kept in the response, when its search tool is missing, turned off, not marked `readOnlyHint: true`, or not visible to apps, as the spec requires. A search runs on every keystroke, so it never stops for approval: a search tool the person set to Ask first is skipped and says so, rather than raising a card per letter.
- Items are `resource_link`s or OpenAI's `{type: "resource", resourceUri, title}` form. Invalid items and duplicates are dropped one by one. Item icons pass through `safeMcpIcons`, and remote ones load without a referrer.
- Choosing an item inserts the same chip an account mention uses. Its source reference names the account and carries the item's URI, title and name (`mentionedResourceSchema` in `chat-sources/reference.ts`). The URI is the identity. The title is only what the chip shows. The chip reads as the item and is exactly as available as its account.
- When the message is sent, and again on every dispatch, the account is rechecked for that chat before anything is read. A chat that lost the account cannot send the mention. Ri then reads each item through the server's `resources/read` and gives the agent an `<ri-mentioned-resources>` block: app, title, URI, name, MIME type and text content, as untrusted data. Text is capped at 32 KiB per item and 96 KiB per message. A binary item is named without its bytes, and a read that fails says why without failing the message.
- `RI_MCP_APPS=0` turns @ search off with the rest of connected apps.

## Files

OpenAI's [file entrypoint](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md#file-extension-entrypoint) makes an app the viewer for the extensions it lists, such as Bits & Bolts' `cad.open` for `.stl`, `.3mf`, `.step` and `.stp`.

- Files come from three places: a chat's attachments, an agent's own folder, and a chat's worktree (an execution's files, where its agent writes). A chat's worktree file shows "Open with" in that chat's Files viewer and opens beside the chat, under the chat's own file rules: on this computer, inside the worktree and reached through real folders, never `.git`, and read only once the chat is archived. When a chat's agent may not use the app, the person can still open their file in it, full screen, where nothing the app does reaches that chat.
- 3D models attach to a chat (`model/stl`, `model/3mf`, `model/step`, whatever name the browser reports), and the agent gets the file's path, as with a zip.

- A chat attachment with a matching extension shows "Open with <app>" beside its chip, and the app opens in the pane beside that chat, as that chat's tab. A file in an agent's folder shows the same control in the Files tab's viewer header, and the app opens full screen on its page. Several matching apps become a menu. Opening calls the entrypoint with OpenAI's `FileInput` through the ordinary approval gate.
- The app never sees a path. Ri gives it an opaque URI (`ri-file:<random id>`) and answers `resources/read`, `resources/subscribe` and `openai/resources/write` for that URI itself (`src/lib/mcp-apps/files.ts`). A view may use only the file it opened, and only its own viewer may. Every other URI still goes to the app's own server.
- A handle names a file by where it lives: an attachment by its stored name, or an agent's file by the agent and a path inside its folder, never a path the browser sent. Each read, watch and save resolves it again with the agent folder's path rules (`sanitizeRelPath`) and checks the path one folder at a time with `lstat`. A symlink anywhere in it, a file with a second hard link, `.git`, and an agent whose folder is on another device are all refused, so no link can alias a file outside the folder or inside `.git`, whatever its name says.
- The file then opens without following a final symlink, the path is checked again, and the open file must be the inode the path names. Reads, the `ifMatch` check and saves all go through that one descriptor, so a folder swapped for a symlink while a read or save is under way cannot redirect it outside the folder. An open that lost the race says the file changed, and trying again works.
- Reads honor `_meta["openai/resource"].representation`. Without one, valid UTF-8 comes back as text and anything else as a base64 blob. Each content item carries `_meta["openai/resource"]` with a content-hash `etag` and `writable`.
- Only a file in an agent's own folder is writable, and not when the agent is archived. An attachment is part of a message's history, so it stays read only. A save compares `ifMatch` with the current etag (`conflict` with the current one), refuses more than 32 MiB (`too-large`), writes in place through the verified descriptor, keeping the file and its mode, and runs one save per file at a time. A save is not atomic: a crash partway through can leave the file partly written. That is the price of a save nothing can redirect, since Node cannot rename a file relative to a folder it has verified (`renameat`), and a rename by path is exactly what a swapped folder redirects.
- A watch follows the file's folder, so an editor's replace-on-save is still seen, and reports only a change in content. The view's own save does not echo back to it, while every other view on the same file hears about it. Ri has no server push for views, so the browser long-polls (`connectedApps.files.changes`, up to 20 seconds per request) and the host relays `notifications/resources/updated`. A watch ends on unsubscribe, as soon as the view closes, or when the view expires.
- The spec amends a file view's tool calls with `_meta["openai/resource"].path`. Ri adds it only for a server on this computer, a catalog command Ri starts or a loopback URL, because the path names this computer's filesystem. A remote server gets no path, since it would mean nothing there and would describe this computer's folders. The engine passes this host-owned `_meta` through `runAction`'s `callMeta`, never from tool input.
- `openai/files/open` is honored only from a server on this computer, for a regular file outside Ri's own home (attachments aside) and never inside an agent's `.git`. The file opens in the asking app's own file viewer when it handles the extension, beside the chat when the view is in one, else full screen. It never goes to a different app without the person choosing it. Otherwise an attachment opens as a download and an agent's file opens the agent's Files tab. A file Ri has no view for is refused.

Not supported, and why:

- Plugin onboarding and the plugin manifest. `onboardingSkill` runs a skill packaged with a plugin when the plugin is installed. Ri connects an MCP server by URL and installs skills one at a time, and plugin bundles (skills and servers installed as one) are not built yet (`docs/skills.md`, "Not built yet"). There is no install moment to run it at. A plugin's skills can still be installed from Plugins, and its server added by URL.
- Picture-in-picture. Ri has no floating view, so `pip` is dropped from a resource's modes and refused on request, as ChatGPT also does.
- ChatGPT's link schemes (`codex://`, `chatgpt://`) and plugin IDs in deep links. Ri reads its own app URL (Deep links).
- `quickAction` on a global entrypoint and `preferredModelDisplayMode` on a tool. OpenAI's SDK accepts them, but the spec does not define what a host does with them. Bits & Bolts declares a quick action, "Choose a part", which Ri ignores.
- Host context Ri does not set: `openai/interactionCursor`. An app defaults to the pointer cursor, which is what Ri would choose.
- Person-added files and folders for remote servers, writes to attachments, and `openai/files/open` from remote servers. These are choices, explained in Forms and Files.

## Bits & Bolts test server

[Bits & Bolts](https://github.com/openai/mcp-extensions/tree/main/plugins/bits-and-bolts) is OpenAI's sample app for its MCP extensions (Apache-2.0): a CAD parts library with a sidebar app, a thread tab, a file viewer, settings, @ search and forms. Ri uses it as the conformance fixture for connected apps, and it is also a useful app to try. `pnpm bits-and-bolts` runs it as a local MCP server.

```sh
pnpm bits-and-bolts start    # build it if needed, then serve http://localhost:3917/mcp
pnpm bits-and-bolts status   # the URL, and whether it is up
pnpm bits-and-bolts stop     # end the server
```

- The first `start` fetches openai/mcp-extensions at a pinned commit and builds it in `~/.local/share/ri-bits-and-bolts` (`BITS_AND_BOLTS_HOME`), outside this checkout. Later starts reuse the build. Changing the pinned commit or the launcher rebuilds it.
- It serves Bits & Bolts' own local store, the same tools, catalog and app as its stdio plugin, on `127.0.0.1` only, with no sign-in. Its screens are self-contained, so they render inside Ri. One handler speaks MCP 2026-07-28 and 2025-era clients. The launcher is `scripts/bits-and-bolts/launcher.mjs`.
- The parts library, imported parts and settings live in `~/.local/share/ri-bits-and-bolts/library` and survive restarts. The log is `server.log` beside it.
- Nothing starts it at login. It runs until `stop`, a restart of the computer, or the process ending. `BITS_AND_BOLTS_PORT` changes the port.
- The repository's remote build (`build:remote`) is not part of this command. Its screens load model files from its own origin, and Ri's sandbox refuses views that need network domains.

To use it in Ri, start the server, then open Settings, Plugins, Add MCP server. Name it "Bits & Bolts", set Server URL to `http://localhost:3917/mcp` and Auth to None, then Add and connect. Ri accepts `http://` only for localhost, which works because the Home's own server connects to it. Bits & Bolts then appears in Apps, the rail's Apps flyout and ⌘K, and Open app shows its parts library full screen. Its Parts Tray opens beside any chat from the app button by the message box, Open with on an `.stl`, `.3mf`, `.step` or `.stp` file opens its viewer, its settings are on its page in Plugins, its parts show in the @ menu, and asking an agent to pick a part shows its form in the chat. This works from any device that can open the Home, since the app's interface reaches the browser through Ri.

To turn it off, switch its connection off or remove it in Settings, Plugins, MCP servers, then run `pnpm bits-and-bolts stop`. A connection left on while the server is stopped shows as unreachable until it is started again.
